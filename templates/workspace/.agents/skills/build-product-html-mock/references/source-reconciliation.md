# 来源汇合规则

## 优先级不是覆盖关系

- PRD、Use Case 和已确认产品规格决定目标、权限、业务行为、必需信息与业务状态。
- Wireflow Mid 决定 Screen、Control、交互状态和分支流转。
- Figma、截图和导出决定视觉层级、资源、排版、尺寸、间距及已设计状态。
- HTML 现有实现只能作为当前证据，不能反向改写上游事实。

来源各自只在其所有权内有效。发生跨边界冲突时，保留双方证据并记录 gap，不做静默裁决。

## 可访问性处理

- `available`：来源可读取，目标 Frame/页面和关键状态足以支撑实现，且已保存可读取、哈希匹配的本地 evidence。
- `partial`：只能读取部分 Frame、截图或导出；在 `gaps` 写明缺少的范围及影响。
- `blocked`：链接无权限、资源损坏或关键页面不可用；停止受影响视觉事实的推导。

不要凭 URL、图层名、缩略图或相邻页面猜测不可访问内容。可继续处理不依赖该来源的已确定工作，但不得把受阻页面声明为完成。

## 汇合步骤

1. 按 Use Case 和 Wireflow 列出应存在的页面、路径、状态和反馈。
2. 清点全部相关 Figma Frame、Prototype 路径、变体、截图与导出资源。
3. 逐个标记来源覆盖范围，不以任意 Group/Frame/Component 名称代替产品语义。
4. 将产品必需但 Figma 未绘制的普通 Web 状态补成视觉实现；涉及新业务语义时记录 gap。
5. 将 Figma 已绘制但产品规格未定义的业务行为记录为冲突，不直接加入 Use Case。
6. 为可用来源保存本地快照/导出并计算 SHA-256，再把每条视觉规则和资源绑定追溯到 Design Source。

## 需要用户确认的情况

只在不可逆或会造成显著返工的用户可见歧义上暂停，例如：互斥的导航结构、关键品牌资源缺失、桌面与移动信息层级相互矛盾。把相关问题合并为少量可运行方案；其余差异用模型 gap 和实现验证继续收敛。
